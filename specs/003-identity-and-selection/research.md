# Research & Decisions: identity-and-selection

> 回填说明：本文件在实现完成后补齐，决策与实际落地代码一致（见 `db.py` / `agent.py` / `main.py` 对应函数）。

## Decision Summary

| # | Decision | Rationale | Alternatives Considered |
|---|---|---|---|
| D1 | **默认账本改为"指向关系"**：新增 `users.default_ledger_id`，`init()` 内做存量回填（优先 owner 名下未删除的「我的账本」，否则最近加入的未删除账本） | FR-012：现状靠名字「我的账本」识别——用户改名即丢锚点、删除即写空。指针与名字解耦，改名零影响 | 继续按名字识别（改名即失效）；新增 `is_default` 布尔列（无法表达"指向唯一账本"语义，且删除后无从回退） |
| D2 | **账本编号 = 内部 id 的展示形式 `#N`**，解析统一走 `resolve_ledger_selector`：`#N`/裸数字 → 在该用户账本列表（**含已删**）中精确匹配；名称唯一 → 直效；名称多命中 → 返回候选 | FR-015/FR-018/FR-022：永久稳定、零迁移；过期编号必然报错而非命中另一账本。编号不引入独立持久化状态 | 动态序号（成员离开后编号塌陷，过期编号会命中**另一个合法账本**——比报错危险）；存储编号（为展示层引入状态与迁移） |
| D3 | **昵称全局唯一 = 唯一索引 + 前置校验 + 存量清理**：`CREATE UNIQUE INDEX idx_users_nickname ON users(nickname)`；`validate_nickname` 先给出友好拒绝；`find_duplicate_nicknames` / `cleanup_duplicate_nicknames` 覆盖存量 | FR-006~FR-010：按名定位（移除/审批/通知）必须唯一命中；并发抢占由索引兜底（至多一个成功）；索引建失败时降级为 warning 而非崩溃 | 仅应用层查重（并发下双写成功）；仅索引无前置校验（用户看到 IntegrityError 而非可读提示） |
| D4 | **回落双保险**：事件内 `_settle_current_ledger(uid, dead_lid)` 确定性改写 `current_ledger_id`（仅当当前指针正指向失效账本）；读时 `_fallback_ledger_id` 兜底链 = **自己的默认账本 → 最近加入的未删除账本 → None（上层明确报错）** | FR-033~FR-035：现状写空值 + 读时按"最近加入"回退，会把用户静默落进**别人的共享账本**。默认优先从根上杜绝误记到他人账上 | 只在读时兜底（指针长期为 NULL，脏状态累积）；只在写时回落（历史脏数据无解——故两者都保留） |
| D5 | **已删账本 = 只读**：`is_ledger_deleted` 守卫嵌入全部 6 个写操作（改名/删除/重置口令/移除成员/审批加入/退出）；记账路径在工具层与 `insert_many_for_ledger` **双重拒绝** | FR-028~FR-030：允许 owner 显式切入已删账本看历史（FR-036 合法只读）后，若不设守卫可在死账本上继续管理，新人会加入已删除账本 | 删除即禁止进入（历史不可查，违背 4.1 软删除可追溯）；只在工具层拦（db 层直调可绕过） |
| D6 | **通知改持久化**：新增 `undelivered_notices` 表（openid / text / created_at），`enqueue_undelivered` 写入、`drain_undelivered` 取走并清空（按 id 升序）；替代 002 的**进程内存 dict** | FR-039~FR-042：内存队列重启即丢；持久化后重启仍在、下次对话补发 | 继续内存队列（重启丢）；写文件（无查询/清理语义，易脏） |
| D7 | **生命周期 = 事件驱动 + 显式 no-op**：`subscribe` → `_build_welcome`（先 `user_exists` 判首关/回来，再 `get_or_create_user` 幂等初始化）；`unsubscribe` → 记日志后返回空串，**零数据变更** | FR-001~FR-005：现状欢迎语停在 001 静态文案、关注不建用户、unsubscribe 完全未处理。取关 ≠ 退账本，数据全保留（与 4.1 软删除精神一致） | 取关自动移出账本（与"取关是平台行为"语义不符）；不做 unsubscribe 分支（加空分支反而制造未定义行为——显式 no-op 更清晰） |
| D8 | **记账人动态显示当前昵称**：`query_by_ledger` LEFT JOIN `users` 取 `created_by_user_id` 的当前 `nickname`；降级路径（`llm.py` 兜底文案）同样带上 | FR-032：与昵称全局唯一自洽（任一时刻一个名字只对应一个人）；身份追溯由内部 id 保证，不依赖展示名 | 昵称快照（昵称可释放再被占用 → 同一名字映射两个不同的人，张冠李戴；且需加快照列与存量回填） |
| D9 | **移除绕过审批的死入口**：`join_ledger` 只产生 `pending` 申请；删除 `tools.query_transactions` / `db.query` 等免账本的遗留查询入口 | FR-037：审批制是唯一入账本通道；遗留入口虽无调用者，但与审批制语义相悖且绕过账本隔离 | 保留但标注弃用（死代码长期存在必然被误用） |
| D10 | **令牌过期判断改单调时钟**：`wechat._token_cache["expires_at"]` 改用 `time.monotonic()` | spec 003 范围外小项（审查项④）：墙钟被 NTP 校时/系统改钟后会误判过期或**永不刷新** | 继续 `time.time()`（低概率但真实存在的误判）；不缓存（触发 2000 次/日上限） |

## Resolved Unknowns

- **默认账本怎么识别才不会被改名/删除破坏？** → D1：指针化 + 删除时自动重建（`_create_default_ledger`），锚点永不落空。
- **同名账本怎么选？** → D2：不猜，返回候选（编号+成员名单）请用户回复编号；候选**实时重算**，不复用历史列表（`resolve_ledger_selector` 每次现查）。
- **已删账本还能不能进？** → D5：**显式切入**可以（只读看历史），但一切写操作被拒；系统默认不把任何人留在已删账本（删除时立即回落，含 owner 本人）。
- **取关后数据怎么办？** → D7：全保留（用户/昵称/账本/成员关系/申请/账目/待补发通知），owner 的共享账本对成员照常可用。
- **通知发不出去怎么办？** → D6 + `_pending_joins_hint`：推送失败入持久化待补发；同时 owner 每次对话自动检查待审批并附在 system prompt 里兜底提示（不依赖 owner 主动查询）。
- **按名定位会不会误伤？** → D3：全局唯一索引 + 前置校验 + 存量清理，任一时刻一个昵称只对应一个人。
- **记账人改名后历史账目显示什么？** → D8：当前昵称（动态），不加快照列。
- **中文昵称长度/换行？** → `validate_nickname`：去空白后非空、≤ 20 字符、不含 `\r`/`\n`。
