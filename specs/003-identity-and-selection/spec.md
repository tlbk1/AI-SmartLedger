# Feature Specification: identity-and-selection

**Feature Branch**: `003-identity-and-selection`

**Created**: 2026-09-15

**Restructured**: 2026-09-16（改为用户旅程主轴组织；落定 Q1 编号方案=内部 id、Q2 记账人显示=动态当前昵称；新增 US1 关注/取关生命周期）；2026-09-17 各 US 补对话样例（示意，非规定文案）；2026-09-17 评审修订：欢迎语告知当前处于默认账本（五要素）、列表/管理确认标出默认账本、删除后立即回落（仅显式切入才停留于已删账本）、删默认账本先确认（新增 FR-014，后续 FR 顺延至 42 条）

**Status**: Draft

**Input**: User description: "把用户视角的逻辑想清楚——多账本下『谁』与『哪本』必须确定：昵称全局唯一、账本用编号+成员名单选择、管理操作可指定账本、默认账本作为永久锚点永不落空、已删账本只读、申请后 owner 能被通知到。"

## 五要素总览

**目标**：把 spec 001/002 遗留的"功能交叉处"问题从系统视角改为**用户旅程视角**收口——用户从**关注 → 建立身份 → 选账本 → 使用 → 离开 → 回来**的全程中，"谁"和"哪本账"在每次交互都确定、可预期。六个子目标：**不猜**（多候选必问，禁止静默取一）、**不空**（默认账本锚点永不落空，当前账本永不为 NULL）、**可引用**（昵称全局唯一，按名定位人永远唯一命中）、**一致**（已删=只读，全程一致）、**不丢**（申请后 owner 必可达：推送或补发）、**有头尾**（关注有引导、取关有定义、回来有延续）。

**输入**：
- 用户动作——关注/取关/再关注事件；消息（设置昵称、记账、查账、创建/加入/切换/管理账本、审批）
- 系统事件——移除成员、退出、删账本、改默认账本名、口令重置、提交申请
- 存量数据——1 用户 / 1 账本 / 0 账目（已盘点，约束可直接建立）
- 上游既有行为——002 的审批制/软删除/两级权限：只补交叉处，不推翻
- 平台约束——48h 客服消息窗口、5s 被动回复、subscribe/unsubscribe 事件

**输出**：
- 规格层——本文件（旅程主轴 8 US）
- 数据层（实现时）——`users.default_ledger_id`、nickname 唯一约束、UndeliveredNotice 持久化表、账本编号=#内部id
- 行为层——每个用户动作/系统事件都有**确定的用户可见响应**（欢迎语、候选列表、拒绝原因、补发通知），没有静默无响应
- 治理层——constitution v1.3.0 原则 VIII（不猜·不空）已同步

**边界**：
- **做**：身份生命周期（关注→取关→再关注）、昵称唯一、账本选择（编号+名称）、管理操作指定账本、默认锚点、已删只读、通知不丢、降级显示记账人
- **不做**（沿用 002）：拒绝申请、申请自动过期、账本转让/多 owner、跨账本统计、账本分组
- **不动**：审批制本身、软删除机制、权限模型、LLM 抽取/总结质量
- **一次性**：存量重名检测与清理（上线前）
- **另走直接小改**：微信令牌过期判断改单调时钟、遗留死代码清理

**成功标准**：双层——旅程节点层（每步定义"用户看到什么 + 系统状态是什么"）× 量化指标层（SC-001~SC-015，见 Success Criteria 章节）。

## 背景：本规格解决什么

spec 001/002 把功能一条条定义了（FR-001~FR-016），但**功能与功能相遇时的行为没有定义**，导致代码在若干"多个候选"的时刻静默替用户做选择，或让内部状态落空。本规格把这些问题作为**一件独立的事**收敛掉，并补上 001/002 都没定义过的**旅程起点与终点**（关注/取关）。

来源：对 spec 002 实现的逐行审查（9 条，见文末「问题追溯」）+ 用户旅程复盘（关注/取关行为未定义）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 关注与回来：旅程有头有尾 (Priority: P1)

新用户首次关注，收到一句**说清楚这个 bot 能干什么**的欢迎语——不只是记账，还包括共账玩法（建账本分享口令、凭口令申请加入）和设置称呼的引导；身份与默认账本在关注时即初始化。用户取关，数据**原样保留**（他是 owner 的共享账本照常可用）；再关注，同一身份无缝延续，一句"欢迎回来"接上之前的进度。

**Why this priority**: 现状欢迎语是 001 时代的静态文案（只提记账），共账能力零引导；关注事件不建用户（懒初始化无成文口径）；unsubscribe 完全未处理——取关后数据如何处置、owner 取关对成员的影响、再关注是否延续，**任何 spec 都没定义过**。旅程的起点和终点是身份（本规格主题）的开始与结束，必须与昵称/账本规则一起定义。

**Independent Test**: 新 openid 关注 → 欢迎语含能力引导五要素且用户已初始化；取关 → 数据零变化；再关注 → 同一 user_id，欢迎语带"欢迎回来"。

**Acceptance Scenarios**:

1. **Given** 新用户首次关注，**When** subscribe 事件到达，**Then** 回复欢迎语，MUST 包含：① 记账用法示例；② 可创建账本并分享口令给家人朋友；③ 可凭口令申请加入他人账本；④ 建议设置称呼（昵称）的引导；⑤ 告知当前处于其默认账本——且该用户身份与默认账本**已初始化**
2. **Given** 用户取关，**When** unsubscribe 事件到达，**Then** 不向其推送任何消息（平台限制），其数据（昵称、账本、成员关系、申请、账目、待补发通知）**全部保留**，权限与成员关系不变
3. **Given** 取关者是共享账本的 owner，**When** 该账本其他成员继续记账/查账，**Then** 一切正常，成员侧无感知
4. **Given** 已取关用户再关注，**When** subscribe 事件到达，**Then** 同一 openid 延续同一身份（昵称/账本/历史原样），欢迎语与首关区分（"欢迎回来"），可附一句当前账本概况
5. **Given** 关注事件丢失或历史存量用户（从未经过 subscribe 初始化），**When** 用户直接发出首条消息，**Then** 身份与默认账本在首条消息时兜底初始化，体验不中断
6. **Given** 取关者名下有未送达的待补发通知，**When** 其再关注后首次对话，**Then** 补发机制照常生效
7. **Given** subscribe 事件重复到达，**When** 系统处理，**Then** 幂等——不重复建用户、不重复建默认账本

**对话样例**（示意，非规定文案；五要素见 FR-001）：

```text
【首次关注】
bot：👋 欢迎使用记账助手！
  · 你现在在自己的默认账本「我的账本」里，直接说「午饭 35」就能记一笔
  · 说「建账本 家用」可创建共享账本，把口令发给家人朋友
  · 拿到别人的口令？发给我即可申请加入（等对方同意）
  · 先给自己起个称呼吧，说「我叫小王」

【再次关注】（同 openid）
bot：👋 欢迎回来！你当前在账本「家用」（#4），随时继续记账。
```

### User Story 2 - 我叫什么：昵称全局唯一，可被可靠引用 (Priority: P1)

用户设置昵称时，若该昵称已被别人占用，系统拒绝并请他换一个。因此任何时刻，一个昵称只对应一个人——"把小明踢了""批准小明"这类按名字的说法永远只命中一个明确的人。

**Why this priority**: 昵称是**被引用的身份标识**（移除成员、审批申请、发送通知都按昵称定位）。当前实现允许重名，且定位处一律"取第一个"，会造成**移除错人/批准错人/通知发错人**。这是身份正确性的根，必须先修。

**Independent Test**: 用户 A 设昵称"小明"，用户 B 再设"小明"→ B 被拒；A 的移除/审批/通知操作始终命中 A 本人。

**Acceptance Scenarios**:

1. **Given** 昵称"小明"已被 A 占用，**When** B 尝试设为"小明"，**Then** 被拒绝，提示"该昵称已被占用，请换一个"，且**不透露占用者是谁**
2. **Given** B 已是某账本成员，**When** B 改名到一个**其他账本**成员正在使用的昵称，**Then** 同样被拒（唯一性范围是**全系统**，不是单个账本）
3. **Given** 用户把昵称改成自己当前的昵称，**When** 提交，**Then** 成功（改名到自身不视为冲突）
4. **Given** 昵称含换行符、或为空、或超过 20 字符，**When** 提交，**Then** 被拒并说明原因
5. **Given** 两个用户同时设置同一个未被占用的昵称，**When** 并发提交，**Then** **至多一个成功**，另一个被拒
6. **Given** 用户改名后，**When** 他人按新昵称定位他（移除/审批/通知），**Then** 命中他本人

**对话样例**（示意，非规定文案）：

```text
用户：我叫小明
bot：✅ 已把你的昵称设为「小明」

（另一用户，昵称已被占用）
用户：我叫小明
bot：该昵称已被占用，请换一个～（不会提示是谁占用的）

（改名到自身当前昵称）
用户：我叫小明
bot：✅ 你的昵称就是「小明」，没变化。
```

### User Story 3 - 我有哪些账本：默认锚点 + 完整列表 (Priority: P1)

每个用户有一个**默认账本**，由"指向关系"确定（不靠名字）：改名不影响指向，删掉需先确认、确认后自动重建。账本列表展示**编号**、名称、角色、成员名单，标出**默认账本**、当前账本与已删除账本——这是用户回答"我有什么"的唯一入口。

**Why this priority**: 默认账本现状靠名字"我的账本"识别——用户改个名，所有回落路径立刻找不到它；删掉它则把当前账本写成空值，用户掉进"无账本"死状态。列表现状无编号无成员名单，同名账本无法区分、历史账本难以发现。

**Independent Test**: 把默认账本改名"我的小账本" → 指向不变（仍是默认，列表中标出）；查看列表 → 每本带编号（#内部id）与成员名单，默认/已删的带标记。

**Acceptance Scenarios**:

1. **Given** 用户改名自己的默认账本，**When** 查看/回落，**Then** 指向关系不受影响，回落目标仍是同一本账
2. **Given** 用户删除自己的默认账本（先经 FR-014 确认），**When** 删除完成，**Then** 自动创建一个新的空默认账本并指向它；用户**有账本可用**，不出现"无账本"状态
3. **Given** 用户有多个账本（含已删除），**When** 查看账本列表，**Then** 每个账本都显示**编号**、名称、自己的角色、成员名单，并标出当前账本、**默认账本**与已删除账本
4. **Given** 同一用户连续两次查看列表，**When** 对比结果，**Then** 编号与成员顺序**完全一致**
5. **Given** 用户查看账本列表，**When** 展示成员名单，**Then** 按 owner 优先、其余按加入顺序；人数过多时截断并标明总人数；只显示昵称，**不出现任何内部身份标识**
6. **Given** 上述改名/删除事件完成后，**When** 检查系统状态，**Then** 该用户始终有默认账本（"默认账本存在率"=100%）

**对话样例**（示意，非规定文案）：

```text
用户：我的账本
bot：你加入的账本（当前：#4，默认：#4）：
  · #4  家用      （owner，成员：老板、小王）← 当前 · 默认
  · #7  我们家    （member，成员：老板、小王、小明）
  · #9  旅行账    （owner，成员：老板，已删除·只读）

（删除默认账本 → 先确认）
用户：删掉家用账本
bot：⚠️ 「家用」（#4）是你的默认账本，删除后：
  · 会自动重建一个空的默认账本，日常记账从零开始（相当于清空）
  · 原账目不会真正删除，历史仍可在原账本查看
  确认删除吗？回复「确认」继续。
用户：确认
bot：✅ 已删除「家用」（#4），已为你重建新的空默认账本「我的账本」（#13），
     当前账本已切过去。
```

### User Story 4 - 我要用哪本：编号或名称指定，重名不猜 (Priority: P1)

用户说"切到 #4"或"切到我们家"来选择账本。名称唯一时直接生效；同名时系统**列出全部候选**（附编号与成员名单）请用户回复编号，绝不默默挑一个。

**Why this priority**: 账本名允许重名（群名模型，两户人家都可能叫"我们家"），名字不是唯一键。当前实现按名字查询"取最近加入的一个"，用户会在未经确认的情况下操作到错误账本——切换还算小事，管理操作（改名/删账本/移除成员）尤其危险。

**Independent Test**: 用户有两个都叫"我们家"的账本 → 说"切到我们家"→ 系统返回候选列表且**不切换**；回复"#4"（候选之一的编号）→ 切到该账本。

**Acceptance Scenarios**:

1. **Given** 某名称只对应一个账本，**When** 用户按名称指定，**Then** 直接生效，无需确认
2. **Given** 用户有两个同名账本，**When** 要求切换到该名字，**Then** 系统返回全部同名候选（含编号与成员名单）并请求回复编号，**不执行切换**
3. **Given** 系统已列出候选，**When** 用户回复编号，**Then** 切换到该编号对应的账本（按 #内部id 精确匹配）
4. **Given** 用户指定的编号未命中其任何账本（含已删除），**When** 提交，**Then** 明确提示（如"没有编号为 #N 的账本"），**不擅自替换为其他账本**
5. **Given** 用户用编号选中一个**已删除**账本，**When** 查看，**Then** 允许（合法只读，带"已删除"提示）；对其发起管理操作由 US6 只读条款拒绝
6. **Given** 用户新加入一个账本，**When** 再次查看列表，**Then** 原有账本的**编号保持不变**（编号=内部 id，天然稳定），新加入的排在末尾
7. **Given** 候选列表展示后账本集合可能已变化，**When** 用户作出选择，**Then** 系统**重新计算**候选，不复用此前展示过的结果

**对话样例**（示意，非规定文案）：

```text
（名称唯一，直接生效）
用户：切到旅行账
bot：✅ 已切到「旅行账」（#9）。

（重名，列候选不猜）
用户：切到我们家
bot：你有两个「我们家」：
  · #7  我们家（成员：老板、小王、小明）
  · #12 我们家（成员：老板、老婆）
  回复编号选择（如「#7」）。
用户：#7
bot：✅ 已切到「我们家」（#7）。

（编号未命中）
用户：切到 #99
bot：没有编号为 #99 的账本。回复「我的账本」可查看你的全部账本。
```

### User Story 5 - 我要管理哪本：管理操作指定账本（含跨账本审批） (Priority: P1)

用户有多本账时，管理操作（改名/删除/重置口令/移除成员/审批加入/查看待审批）作用于**用户指定的**账本。未指定时系统先问清是哪一本；只有一本账时直接执行。

**Why this priority**: 当前管理操作**只能作用于当前账本**，且审批相关的查询在数据层就**没有"指定账本"的入口**——多账本 owner 在**非当前账本**的待审批申请**完全无法查询和处理**，审批制在多账本场景下实际不可用。

**Independent Test**: 用户有 A、B 两账本，B 有新申请 → 用户问"有哪些申请"并能指定 B → 能看到 B 的申请并批准。

**Acceptance Scenarios**:

1. **Given** 用户有多个账本，**When** 发起管理操作但未指明账本，**Then** 系统先展示账本列表（编号+名称+成员，并标出当前/默认账本）请其确认
2. **Given** 用户指定账本 B，**When** 执行管理操作，**Then** 仅影响 B，其他账本不受影响
3. **Given** 用户只有一个账本，**When** 发起管理操作，**Then** 直接执行，不额外询问
4. **Given** owner 当前在账本 A、账本 B 有待审批申请，**When** 查询待审批并指定 B，**Then** 能看到 B 的申请（含申请人昵称）
5. **Given** owner 指定账本 B 批准一条申请，**When** 执行，**Then** 申请人成为 B 的成员，A 不受影响
6. **Given** 用户在当前账本对话，**When** 他还没开口提问，**Then** 系统**不会**把其他账本的待审批数量当成当前账本的提示而混淆

**对话样例**（示意，非规定文案）：

```text
用户：有哪些申请？
bot：你有多个账本，要查哪一本的申请？
  · #4  家用      （owner）← 当前 · 默认
  · #7  我们家    （owner）
用户：#7
bot：「我们家」（#7）有 1 条待审批申请：
  · 小王（9月16日 20:15）
  回复「同意 小王」即可通过。
用户：同意 小王
bot：✅ 已同意「小王」加入「我们家」（#7）。

（只有一个账本时，不问）
用户：有哪些申请？
bot：「家用」目前没有待审批的加入申请。
```

### User Story 6 - 账本删了之后：只读一致 + 记账人可见 (Priority: P2)

账本被删除后，其成员（含 owner）的当前账本**立即回落**到各自默认账本——系统默认**不**把任何人留在已删除账本里；用户仍能通过**显式切换**进入已删账本查看历史（带"该账本已被删除"提示），但一切写操作都被拒绝。历史账目里**每笔都显示是谁记的**——即使智能总结环节不可用（降级为固定文案）也不例外。

**Why this priority**: 允许 owner **显式切入**已删账本查看历史（合法只读状态）后，六个管理操作都没有检查删除状态——owner 可以在一个已删除的账本上说"批他进来"，新人就会加入一个已删除的账本（状态一致性）。记账人显示在降级路径缺失，使"可显示记账人的账目比例=100%"不成立。

**Independent Test**: 删除账本 → 原当前账本指向它的用户（含 owner）立即回落默认；显式切入已删除账本后依次尝试改名/批准/移除/重置口令/再删除 → 全部被拒并提示"该账本已被删除（只读）"；强制降级查账 → 每笔账仍带记账人昵称。

**Acceptance Scenarios**:

1. **Given** 账本被删除，**When** 删除完成，**Then** 当前账本指向该账本的所有用户（**含执行删除的 owner 本人**）的当前账本已回落到各自默认账本——系统默认不把任何人留在已删除账本
2. **Given** 用户**显式切换**进入已删除账本，**When** 查看，**Then** 允许（合法只读），并提示"该账本已被删除"
3. **Given** 用户已显式切入已删除账本，**When** 尝试改名，**Then** 被拒 + 提示"该账本已被删除（只读）"
4. **Given** 同上，**When** 尝试批准一条加入申请，**Then** 被拒
5. **Given** 同上，**When** 尝试移除成员 / 重置口令 / 退出，**Then** 均被拒
6. **Given** 账本已被删除，**When** 再次请求删除，**Then** 明确提示"已删除"，且**原删除时间不被覆盖**
7. **Given** 账本已被删除，**When** 查看历史账目，**Then** 正常可见，带"该账本已被删除"提示，**每笔账显示记账人昵称**
8. **Given** 账本已被删除，**When** 尝试记账（含**显式指定**记到该账本），**Then** 被拒（双重防御保持，不可回退）
9. **Given** 智能总结不可用（降级文案），**When** 用户查账，**Then** 结果每笔账都显示记账人昵称
10. **Given** 智能总结可用，**When** 用户查账，**Then** 每笔账显示记账人昵称（现状已成立，不得回退）

**对话样例**（示意，非规定文案）：

```text
（账本被删除后，当前账本已自动回落——正常记账落在存在的账本，不受影响）
用户：记一笔 30 餐饮
bot：✓ 已记 1 笔（当前账本：家用）。

（显式切入已删除的账本 → 只读查看历史，带记账人）
用户：切到旅行账
bot：已切到「旅行账」（#9）——该账本已被删除（只读，仅能查看历史账目）。
用户：查上月账单
bot：「旅行账」（#9）上月共 2 笔，支出 ¥62：
  · 8月30日 午饭 -32（老板）
  · 9月2日 打车 -30（小王）
  ⚠️ 该账本已被删除，仅供查看历史。

（显式指定往已删除账本记账，被拒）
用户：把这笔 30 餐饮记到旅行账
bot：操作失败：账本「旅行账」（#9）已被删除（只读），不能记账。

（对已删除账本做管理操作，被拒）
用户：把旅行账改名为「旧账」
bot：操作失败：该账本已被删除（只读），无法改名。
```

### User Story 7 - 离开账本之后：回落不落空 (Priority: P1)

无论被 owner 移出、主动退出，还是当前账本被删除，用户的当前账本都**确定地回落到他自己的默认账本**——永不写空、永不悬空、永不静默落进别人的账本；删除事件完成后系统默认**不把任何人留在已删除账本**（含删除者本人），只有用户**显式切换**才进入已删账本（只读）。用户显式切入的只读状态不被兜底逻辑改写。

**Why this priority**: 现状三条失效路径的回落都可能在默认账本取不到时把 `current_ledger_id` 写成 NULL（用户掉进"无账本"死状态，所有操作失效）；读时兜底又按"最近加入"回退，可能把用户落进**别人的共享账本**，下一笔记到别人账上。

**Independent Test**: 用户把默认账本改名为"我的小账本" → 从共享账本退出 → 当前账本回落到"我的小账本"（不是空、也不是别人的账本）。

**Acceptance Scenarios**:

1. **Given** 用户被 owner 移出共享账本（其当前账本正是该账本），**When** 操作完成，**Then** 当前账本回落到**他自己的默认账本**
2. **Given** 用户主动退出共享账本（其当前账本正是该账本），**When** 退出完成，**Then** 当前账本回落到**他自己的默认账本**
3. **Given** 用户的当前账本引用丢失或指向已失效账本（历史脏数据），**When** 他记账/查账，**Then** 系统按「**自己的默认账本 → 最近加入的账本 → 明确报错**」兜底
4. **Given** 用户加入过他人的共享账本，**When** 发生兜底回落，**Then** **不会**把别人的账本当默认目标（下一笔账不会记到别人账上）
5. **Given** 上述任一事件（被移除/退出/当前账本被删）完成，**When** 检查系统状态，**Then** 用户的当前账本**有有效取值**（不为 NULL、不悬空）
6. **Given** 用户显式切入一个已删除账本查看历史，**When** 兜底逻辑运行，**Then** 其显式选择**不被改写**

**对话样例**（示意，非规定文案）：

```text
（小王此前当前账本是「我们家」#7，被 owner 移出；他的默认账本是「家用」#4）
用户（小王）：记一笔 20 交通
bot：✓ 已记 1 笔（当前账本：家用）。
     你已不在「我们家」，账目记入了你自己的「家用」。

（主动退出）
用户：退出我们家
bot：✅ 已退出「我们家」（#7）。你的历史账目仍保留在该账本里，
     当前账本已切回「家用」（#4）。
```

### User Story 8 - 有人申请之后：通道唯一 + 通知不丢 (Priority: P2)

有人提交加入申请后，系统**主动尽力通知 owner**；通知发不出去时**记录下来**，不静默丢弃，服务重启也不丢，owner 下次对话补发提示。而"成为成员"自始至终只有一条通道：口令申请 → owner 审批。

**Why this priority**: spec 002 明确定义了"审批流程第 2 步：尽力推送通知 owner"，但这一步完全没有实现——申请人提交后，owner 只能靠自己主动发起对话才可能看到。遗留的"凭口令直接加入"死代码入口虽无调用者，但与审批制语义相悖，必须移除。通知队列现状存进程内存，重启即丢。

**Independent Test**: 申请人提交 → owner（在互动窗口内）收到通知；把推送模拟为失败 → 该通知进入待补发记录，服务重启后仍在，owner 下次对话被补发。

**Acceptance Scenarios**:

1. **Given** 申请人提交了一条申请，**When** 系统尝试通知 owner，**Then** 通知包含申请人昵称与账本名，并说明如何查看/处理
2. **Given** owner 在 48h 互动窗口内，**When** 推送成功，**Then** owner 收到通知
3. **Given** owner 在窗口外（推送必然失败），**When** 提交申请，**Then** 申请流程**正常完成、不被阻塞**，该通知被记录待补发
4. **Given** 生成通知的过程中出错（如查询昵称/账本名失败），**When** 异常发生，**Then** 该通知仍被记录待补发，**不静默丢失**
5. **Given** 有未送达的通知，**When** 服务重启，**Then** 待补发记录**仍然存在**（不因重启永久丢失）
6. **Given** owner 长期未上线，**When** 他下次对话，**Then** 未送达的通知被补发提示
7. **Given** 任何用户凭口令尝试加入，**When** 系统处理，**Then** 只能产生**待审批申请**，不存在绕过审批直接成为成员的路径

**对话样例**（示意，非规定文案）：

```text
（申请人在窗口内 → owner 收到推送）
bot → owner：📢 「家用」（#4）有新的加入申请：小王（9月16日 20:15）。
             回复「有哪些申请」查看；说「同意 小王」通过。

（推送失败 → owner 下次对话时补发，不丢）
用户（owner）：今天午饭 45
bot：✓ 已记 1 笔（当前账本：家用）。
[补发] 「家用」（#4）有新的加入申请：小王（9月16日 20:15）。
       说「有哪些申请」可查看。
```

### Edge Cases

- 用户**改名到别人已占用的昵称** → 拒绝；改到自己当前的昵称 → 允许。
- **昵称占用范围是全系统**：即使两人不在任何共同账本，也不能同名（有意取舍，见 Assumptions）。
- **两个账本同名** → 列候选（编号+成员名单），不猜。
- 用户**离开一个账本后**再查看列表 → **编号不变**（编号=内部 id，永久稳定）；离开的账本从列表消失，其余账本编号不受影响（无塌陷）。
- 用户**被移出账本后可重新申请同一账本**（沿用 002 已确认行为，本规格不改变）。
- 默认账本被删时，**别人可能正把它当作共享账本使用** → 删除只影响 owner 自己的指向，其他成员各自的回落目标不受影响。
- 默认账本被删除后**自动重建**，用户会"多出"一个新账本 → 属有意取舍（"清空重来"是真实需求，锚点永不消失的权重更高）；删除前有**显式确认**（FR-014）。
- 历史脏数据：**已有默认账本被改名/被删**的存量用户 → 由兜底链（默认 → 最近加入 → 报错）消化。
- 用户**显式切换进入已删除账本**（合法只读状态）→ 不得被兜底逻辑改写；**删除事件本身**会立即回落所有人的当前账本（含 owner），系统默认不把任何人留在已删账本（FR-033/FR-036）。
- 已删除账本**仍出现在账本列表中**（带"已删除·只读"标记）→ 占用编号，可被编号选中查看（对其管理操作被 US6 拒绝）。
- 记账人**改名后**，其历史账目的记账人显示**当前昵称**（动态；身份追溯由内部 id 保证，见 FR-032）。
- **subscribe 事件重复到达** → 幂等：不重复建用户、不重复建默认账本（UNIQUE openid 兜底）。
- **关注事件丢失/历史存量用户** → 首条消息兜底初始化（FR-002）。
- **取关者是某共享账本 owner** → 账本照常可用，成员无感知；不做自动转让/自动移出。

## Requirements *(mandatory)*

### Functional Requirements

**US1 关注与回来（生命周期）**

- **FR-001**: 首次关注的欢迎语 MUST 包含五要素：① 记账用法示例；② 可创建账本并分享口令；③ 可凭口令申请加入他人账本；④ 设置称呼（昵称）的引导；⑤ 告知用户**当前正处于自己的默认账本**（初始化完成，可直接开始记账）。规格确定**要素**，不限定全文措辞。
- **FR-002**: 用户身份与默认账本 MUST 在 subscribe 事件到达时初始化（幂等）；关注事件缺失时 MUST 在首条消息兜底初始化，不得中断体验。
- **FR-003**: 取关 MUST 保留该用户全部数据（用户、昵称、账本、成员关系、申请、账目、待补发通知），MUST NOT 改变任何权限或成员关系。
- **FR-004**: 取关者名下账本（含其为 owner 的共享账本）MUST 对其余成员照常可用。
- **FR-005**: 再关注（同 openid）MUST 延续原身份；欢迎语 MUST 与首关区分（"欢迎回来"），MAY 附当前账本概况。

**US2 我叫什么（昵称全局唯一）**

- **FR-006**: 系统 MUST 保证**昵称全局唯一**——同一时刻一个昵称只属于一个用户，跨账本亦然。
- **FR-007**: 设置已被占用的昵称时，系统 MUST 拒绝并提示"该昵称已被占用，请换一个"，且 MUST NOT 透露占用者身份。
- **FR-008**: 系统 MUST 校验昵称合法性：非空、去空白后非空、长度 ≤ 20 字符、不含换行符；不满足 MUST 拒绝并说明原因。
- **FR-009**: 系统 MUST 在数据层维护昵称唯一性约束，使**并发**设置同一昵称时至多一个成功。
- **FR-010**: 昵称唯一性约束的启用 MUST 以**存量数据无重名**为前提；上线前 MUST 提供存量重名检测与清理手段。
- **FR-011**: constitution 与 spec 001 中"账本内唯一 / 跨账本允许重名"的条款 MUST 同步修订为"全局唯一"，并记录取舍理由。

**US3 我有哪些账本（锚点 + 列表）**

- **FR-012**: 每个用户 MUST 有一个**由指向关系确定**的默认账本（`users.default_ledger_id`）；账本改名 MUST NOT 影响该指向。
- **FR-013**: 默认账本被删除时，系统 MUST 自动创建新的空默认账本并更新指向，使用户始终有账本可用。
- **FR-014**: 删除**默认账本**时，系统 MUST 先请用户确认，并明确告知后果（删除后将自动重建一个**空的**默认账本，日常记账从零开始、相当于清空；原账目为软删除，历史仍可在原账本查看）；未经确认 MUST NOT 执行删除与重建。非默认账本的删除沿用 002 现状，不强制额外确认。
- **FR-015**: 账本列表 MUST 展示每个账本的**编号**、名称、用户在该账本的角色、成员名单（含当前账本标记、**默认账本标记**、已删除标记）；同一用户连续两次查看，编号与成员顺序 MUST 一致。
  - **编号方案（已定）**：编号 = 账本**内部 id**，展示为 `#N`。理由：永久稳定（不随加入/离开/删除重排）、零迁移成本；过期/未命中编号必然报错而非命中其他账本；已删除账本天然仍占编号。**否决记录**：动态序号——成员离开后编号塌陷，过期编号会命中**另一个合法账本**（违反 FR-021 的"不得替换"精神，比报错危险）；存储编号——为纯展示层引入持久化状态、分配逻辑与存量迁移。
- **FR-016**: 成员名单 MUST 按**稳定顺序**展示（owner 优先，其余按加入顺序），人数过多时 MUST 截断并标明总人数。
- **FR-017**: 成员名单 MUST 只包含昵称，MUST NOT 包含任何内部身份标识。

**US4 我要用哪本（选择）**

- **FR-018**: 用户 MUST 能用**编号或名称**指定账本。编号格式 `#N`（或裸 `N`），解析 MUST 按内部 id **精确匹配该用户已加入的账本列表（含已删除）**；未命中 MUST 明确报错，MUST NOT 按位置/序号/最近加入解释。
- **FR-019**: 名称对应**多个**账本时，系统 MUST NOT 自行选择，MUST 返回全部同名候选（含编号与成员名单）并请用户回复编号。
- **FR-020**: 名称**唯一**时 MUST 直接生效，无需确认。
- **FR-021**: 名称**不存在**、或编号未命中时，系统 MUST 明确提示，MUST NOT 替换成其他账本。
- **FR-022**: 候选列表 MUST 在用户作出选择时**重新计算**，MUST NOT 复用此前展示过的结果。

**US5 我要管理哪本（指定账本的管理操作）**

- **FR-023**: 管理操作（改名 / 删除 / 重置口令 / 移除成员 / 审批加入 / 查看待审批）MUST 支持指定目标账本。
- **FR-024**: 用户有**多个**账本且未指明目标时，系统 MUST 先请用户确认账本（展示编号+名称+成员，并**标出当前/默认账本**），MUST NOT 静默作用于当前账本。
- **FR-025**: 用户只有**一个**账本时，MUST 直接执行，不额外询问。
- **FR-026**: 待审批申请 MUST 能**按指定账本**查询（含申请人昵称），MUST NOT 仅限于当前账本。
- **FR-027**: 权限判定 MUST 基于**目标账本**内的角色（沿用 002 FR-004，不得回退）。

**US6 账本删了之后（只读 + 记账人）**

- **FR-028**: 已删除账本 MUST 为只读：改名 / 删除 / 重置口令 / 移除成员 / 审批加入 / 退出 MUST 全部被拒，并提示"该账本已被删除（只读）"。
- **FR-029**: 对已删除账本重复删除 MUST 明确提示"已删除"，MUST NOT 覆盖原删除时间。
- **FR-030**: 向已删除账本记账 MUST 被拒（沿用现状，双重防御保持）。已删除账本的口令 MUST 继续失效。
- **FR-031**: 已删除账本的**历史账目 MUST 仍可查看**（沿用 002 FR-015），并 MUST 带"该账本已被删除"提示。
- **FR-032**: 查账结果 MUST 在正常与降级两条路径下都显示每笔账的记账人昵称。**记账人改名后，历史账目显示当前昵称（动态，已定）**——展示时按 `created_by_user_id` 关联用户当前昵称。取舍：与昵称全局唯一自洽（任一时刻一个名字只对应一个人，同一人所有账目永远显示同一名字）；**否决记录**：昵称快照——昵称可释放再被占用后，同一名字会映射到两个不同的人（张冠李戴），且需加快照列与存量回填；身份追溯由 `created_by_user_id` 内部 id 保证（constitution 2.2：归属不变）。

**US7 离开账本之后（回落）**

- **FR-033**: 使当前账本失效的事件（被移除 / 主动退出 / 当前账本被删）MUST 使当前账本回落到**用户自己的默认账本**——**含执行删除的 owner 本人**；删除完成时系统默认不把任何用户留在已删除账本。
- **FR-034**: 当前账本引用 MUST NOT 被写为空值；上述事件完成后，用户的当前账本 MUST 有有效取值。
- **FR-035**: 当前账本引用丢失或指向失效账本时，系统 MUST 按「**自己的默认账本 → 最近加入的账本 → 明确报错**」的顺序兜底；MUST NOT 静默落入与他人共享的账本作为首选。
- **FR-036**: 用户**显式切换**进入的当前账本（含已删除账本这一合法只读状态）MUST 被尊重，MUST NOT 被兜底逻辑改写；**除显式切换外**，系统 MUST NOT 使当前账本指向已删除账本（回落规则见 FR-033）。

**US8 有人申请之后（通道唯一 + 通知）**

- **FR-037**: 成为账本成员的唯一通道 MUST 是"口令申请 → owner 审批"；遗留的绕过审批直接加入入口 MUST 移除。
- **FR-038**: 申请提交后，系统 MUST **尽力**通知账本 owner（推送含申请人昵称与账本名）。
- **FR-039**: 通知投递失败时，该通知 MUST 进入**待补发记录**，MUST NOT 静默丢弃；申请流程 MUST NOT 被阻塞。
- **FR-040**: 生成通知过程中发生异常时，该通知 MUST 同样进入待补发记录（在目标可得的前提下）。
- **FR-041**: 待补发记录 MUST **在服务重启后仍然存在**（持久化，不再仅存于内存）。
- **FR-042**: 有未送达通知时，用户下次对话 MUST 被补发提示。

### Key Entities

- **User**：用户。`nickname`（**全局唯一**的展示名，可被引用）、`current_ledger_id`（当前账本，**永不为空**）、`default_ledger_id`（**新增**：默认账本指向，作为永久锚点，替代按名字识别）。
- **Ledger**：账本。`name`（**允许重名**，群名模型）、owner、口令、删除时间。展示层附**编号**（= 内部 id 的展示形式 `#N`，规则见 FR-015）。
- **LedgerMember**：成员关系（账本、用户、角色 owner/member、加入时间）。决定成员名单的稳定顺序与权限判定。
- **JoinRequest**：加入申请（账本、用户、状态、时间）。可按指定账本查询（FR-026）。
- **Transaction**：账目。含记账人归属（`created_by_user_id`）；展示时动态关联其当前昵称（FR-032）。
- **UndeliveredNotice**（**新增**）：待补发通知（目标用户、文本、生成时间）。持久化，使通知不因投递失败或服务重启而丢失。

## Success Criteria *(mandatory)*

### 旅程节点层（每步"用户看到什么 + 系统状态是什么"）

| 旅程节点 | 用户看到 | 系统状态 |
|---|---|---|
| 首次关注 | 欢迎语（五要素：记账示例/建账本/凭口令加入/设置称呼/当前处于默认账本） | 身份 + 默认账本已初始化（幂等） |
| 首条消息（事件丢失兜底） | 正常响应，体验不中断 | 兜底初始化完成 |
| 设置称呼 | 成功确认 / 占用拒绝（不透露占用者） | nickname 全局唯一 |
| 查看账本 | 编号 #id + 名称 + 角色 + 成员名单 + 当前/默认/已删标记 | 列表确定、两次一致 |

### 量化指标层

- **SC-001** (US2): 尝试设置已被占用昵称时，被拒率 = **100%**（跨账本亦然）。
- **SC-002** (US2): 按昵称定位成员的操作（移除 / 审批 / 通知）命中唯一明确目标的比例 = **100%**，误伤他人 = **0 次**。
- **SC-003** (US3): 任意时刻，"没有默认账本"的用户比例 = **0%**（含"默认账本被改名"与"默认账本被删除"之后）。
- **SC-004** (US3): 账本列表连续两次展示，编号与成员顺序一致率 = **100%**。
- **SC-005** (US3): 账本列表展示的成员名单中，出现内部身份标识的次数 = **0**。
- **SC-006** (US4): 存在同名账本时，系统**自行选择**账本的比例 = **0%**（必须列候选）。
- **SC-007** (US4): 用户用编号或名称指定账本的成功率 = **100%**（唯一名称与合法编号）。
- **SC-008** (US5): 管理操作作用于**非用户指定**账本的比例 = **0%**。
- **SC-009** (US6): 已删除账本上的写操作被拒率 = **100%**。
- **SC-010** (US6): 查账结果（正常与降级路径）中，可显示记账人昵称的账目比例 = **100%**。
- **SC-011** (US7): 因被移除 / 退出 / 账本被删而处于"当前账本为空"状态的用户数 = **0**。
- **SC-012** (US8): 提交申请后，系统**发起** owner 通知的比例 = **100%**（48h 窗口内送达为尽力而为，窗口外计入待补发）。
- **SC-013** (US8): 通知静默丢失率 = **0%**（含生成异常路径与服务重启）。
- **SC-014** (US1): 首关欢迎语五要素齐全率 = **100%**；关注后身份与默认账本初始化完成率 = **100%**。
- **SC-015** (US1): 取关导致的数据丢失 = **0 例**；再关注后身份延续率 = **100%**。

## Assumptions

- **昵称全局唯一 = 用户名模型（先到先得）**：与"账本内唯一（群昵称模型）"相反。代价是常见名会先到先得、规模化后好名字耗尽——属**有意取舍**（昵称是必须被引用的身份，唯一性优先于自由度）。
- **账本名允许重名 = 群名模型**：两户人家都可以叫"我们家"，要求全局唯一既不合理也无法协商。因此"允许重名"与"名字可作唯一键"是两件事——修复点在**选择机制**，不在名字唯一性。（与昵称策略相反，这是刻意的。）
- **编号 = 内部 id 的展示形式（`#N`）**：不引入独立编号状态、无迁移；已删除账本也占用编号（带标记）；数字可能不连续或偏大（如 #3、#17），属可接受的 cosmetic 代价；内部 id 对用户可见不构成安全风险（授权靠成员关系，不靠 id 保密）。
- **记账人动态显示当前昵称**：历史账目的显示会随记账人改名而变化——属有意取舍（与全局唯一模型自洽；快照在昵称可释放再占用下会张冠李戴）；审计追溯由内部 id 保证。
- **欢迎语定要素、不定全文**：FR-001 规定 MUST 包含的五个要素；具体措辞在实现阶段定，允许后续运营调优。
- **取关 = 数据保留**：微信取关 ≠ 退账本——用户数据、成员关系、账目全部保留；不做取关自动移出账本、不做自动转让。与 constitution 4.1（软删除、账目永不物理删除）精神一致。
- **首关/再关注区分依据 = 用户是否已存在**（同 openid 已有用户记录），不依赖微信 subscribe 场景值。
- **被移除 / 已退出的成员可重新申请同一账本**：沿用 002 已确认行为，本规格不改变。
- **默认账本自动重建是有意的取舍**：用户会"多出"一个新账本，但"清空重来"是真实需求，且默认账本作为回落锚点**永不消失**的权重更高；删除前的确认提示（FR-014）保证用户知情。
- **删除确认仅对默认账本强制**：默认账本的删除对用户数据影响最大（个人日常记账"清空重来"），故必须确认；共享账本的删除沿用 002 现状（工具已有 confirm 参数），不额外加流程。
- **不做"发现缺失即静默重建"**：重建只发生在**显式删除默认账本**时，不在回落路径上静默执行（避免用户以为自己 200 笔账"凭空消失"）。
- **本期仍不实现**「拒绝申请」与「申请自动过期」：`rejected` 为预留状态；`expired` 仅用于口令重置时作废旧申请。列为后续增强。
- **推送窗口限制沿用 002**：微信客服消息只能发给 48h 内互动过的用户；因此"通知 owner"仍是**尽力而为**，主通道（FR-038）与兜底提示（002 已实现）并存。
- **存量数据现状（已盘点，2026-09-15）**：库内 1 用户 / 1 账本 / 0 账目；**无重名昵称、无空当前账本、默认账本未改名未删除** → 本规格涉及的约束可**直接建立**，迁移零风险；检测与清理手段仍须实现，以覆盖未来数据。
- **超出本规格范围的小项**（另行直接修复，不经本流程）：微信访问令牌过期判断改用单调时钟；清理遗留的未使用查询入口。
- **不做**：账本转让 / 多 owner；跨账本聚合统计；账本层级或分组。
