# Feature Specification: query-accuracy

**Feature Branch**: `feat/002-shared-ledger`（004 在该分支上推进，随 PR #1 一起提交）

**Created**: 2026-10-01

**Status**: Draft

**Input**: User description: "查账重构：合计由 SQL 聚合（不再受 limit 影响），明细降为「金额最大的 5 笔」——「这个月花了多少」是本 bot 最高频的问题，也是唯一在不报错的前提下给出错误答案的路径。"

**来源**: PR #1 评论〈查账重构：合计由 SQL 聚合〉（2026-09-30）+ 评审时补充的 3 个盲点（2026-10-01，逐条复现核验）。

## 五要素总览

**目标**：让"这个月花了多少钱"这类最高频问题的答案**永远准确**——合计由 SQL 聚合产出，与返回多少条明细彻底无关；明细降级为"佐证"，按金额排序让用户能拿大头核对合计；收入/支出天然分开，不再出现把两者加在一起的"总金额"。

**输入**：
- 用户消息——金额类问题（"这个月花了多少""上个月餐饮花了多少"）、明细类问题（"最近买了啥"）
- 现状代码——`query_transactions`（limit 默认 20、docstring 未提截断）、`db.query_by_ledger`（`ORDER BY happened_at DESC LIMIT ?`）、`llm.summarize_query_result`（`sum()` 心算且不区分收支）
- 两条查询路径——主路径（ReAct LLM 读 JSON 自行心算）与兜底路径（`graph.py` 固定路由 → `llm.summarize_query_result`）

**输出**：
- 数据层——`db.sum_by_ledger(...)`（无 LIMIT 的按类型聚合）；`query_by_ledger` 支持 `order_by`
- 工具层——`query_transactions` 返回统一信封 `{records, totals, total_count, order_by}`；limit 默认 5、钳制 [1, 50]
- 展示层——总结 prompt 与降级文案均基于 `totals`（支出/收入分开表述）
- 两条路径同口径——主路径（提示词）与兜底路径（`graph.py`）都不得再从明细心算

**边界**：
- **做**：聚合正确性、收支分列、明细降级为"金额最大 ≤5 笔"、工具返回结构统一（含已删账本分支）、兜底路径同步、降级文案同步
- **不做**：分页/翻页、账目导出、按成员聚合、时间趋势/图表、明细"查看更多"交互
- **不动**：记账写入路径、账本隔离机制、记账人昵称展示（SC-010 须保持）

**成功标准**：见 Success Criteria（复现场景归零 + 两层查询路径同口径 + 既有保证不回归）。

## 背景：本规格解决什么

「这个月花了多少」是全 bot 最高频的问题，也是**唯一"不报错却给错答案"的路径**：

1. `query_transactions` 的 `limit` 默认 20（`agent.py:75`），透传给 `query_by_ledger` 的 `ORDER BY t.happened_at DESC LIMIT ?`（`db.py:810`）；
2. **db 层没有任何 `SUM` 聚合**——合计由行内心算（主路径：ReAct LLM 读返回的行自己加；兜底路径：`llm.py:335` 的 `sum(r["amount"] for r in rows)`，且**不区分收支**）；
3. 工具 docstring 未提 limit，LLM 不知道有截断，也不会主动调大。

**诊断核验（2026-10-01，逐条复现）**：造 25 笔支出、合计 ¥1250（其中一笔 290 的大额在月初）→ 工具按默认 limit=20 返回最近 20 笔、之和 ¥800 → 回复会报 **¥800.00**，且无任何"数据不完整"迹象。金额越集中在早期，缩水越严重。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 合计永远准确：与明细条数彻底解耦 (Priority: P1)

用户问"这个月花了多少钱"，回复里的合计来自**数据库聚合**——不管账本里有 25 笔还是 250 笔、明细只列几条，合计都是全量之和；收入与支出分开报，不再混加。

**Why this priority**: 这是唯一"不报错但给错答案"的路径，直接损害用户对账本的信任；且修复点是"合计的产出方式"，不是调参——不改则永远存在。

**Independent Test**: 造 25 笔支出（合计 1250，含一笔 290 大额）→ 问"这个月花了多少" → 合计必须是 1250 而不是 800。

**Acceptance Scenarios**:

1. **Given** 本月 25 笔支出、合计 ¥1250（含一笔 ¥290 大额），**When** 用户问"这个月我花了多少钱"，**Then** 合计 = **¥1250.00**（全量），且回复不暗示"只看了一部分"
2. **Given** 同账本有一笔 ¥5000 收入，**When** 用户问支出，**Then** 支出合计不含该收入；用户问"收支情况"时，**Then** 支出/收入分列（`GROUP BY type`）
3. **Given** 空账本，**When** 用户查合计，**Then** 回复"没有记录"类文案，totals 为 0，**MUST NOT 编造金额**
4. **Given** 用户在"餐饮"分类下有 3 笔、其他分类 20 笔，**When** 问"餐饮花了多少"，**Then** 合计只含餐饮 3 笔
5. **Given** 账本有 250 笔（远超任何 limit），**When** 问合计，**Then** 合计仍然准确（聚合与明细解耦）

**对话样例**（示意，非规定文案）：

```text
（本月实际 26 笔：支出 25 笔共 ¥1,250，收入 1 笔 ¥5,000）
用户：这个月我花了多少钱
bot：本月共 26 笔——支出 ¥1,250.00（25 笔）、收入 ¥5,000.00（1 笔）。
     花得最多的几笔：房租 -¥800（9-01）、聚餐 -¥220（9-15）……
```

---

### User Story 2 - 明细降为"金额最大的 5 笔"：拿到大头，核对得上 (Priority: P1)

明细的职责从"尽量列全"改为"让用户能拿大头核对合计"——默认按金额降序返回最多 5 笔；需要浏览"最近买了啥"时，按时间序返回。

**Why this priority**: 明细条数直接决定用户对合计的信任——若明细只列最近 5 笔小额，用户会怀疑合计算错；按金额排序让"最大几笔 + 合计"能对上，合计可信。且默认值改动即改变九成查询行为（LLM 多数不传 limit）。

**Independent Test**: 造 3 笔（少于默认值）→ 全列且 `total_count` 正确；造 25 笔 → 只列金额最大的 5 笔、按金额降序。

**Acceptance Scenarios**:

1. **Given** 任意账本，**When** 用户查账，**Then** 明细 ≤5 条、按金额降序（金额最大的在前）
2. **Given** 用户问"最近买了啥/最近记了什么"，**When** 工具被调用，**Then** LLM 显式指定时间序（`order_by="recent"`），明细按时间倒序
3. **Given** LLM 显式传 `limit=20`，**When** 查询执行，**Then** 返回 20 条；传 `limit=999` → 钳制为 50；传 `limit=0` 或负数 → 钳制为 1（不报错、不穿透）
4. **Given** 账本只有 3 笔，**When** 查账，**Then** 明细 3 条全列，`total_count=3`
5. **Given** 明细只列了大头，**When** 用户对照合计，**Then** 回复**MUST NOT** 让用户误以为"账目只有这几条"（文案说明这是"最大的几笔"）

**对话样例**（示意，非规定文案）：

```text
用户：这个月都买了啥
bot：本月共 26 笔。按时间倒序最近 5 笔：……
     （需要看全部明细请说「列全部本月账目」）

用户：上个月买了个啥大件来着
bot：上个月金额最大的一笔是 9-15 的聚餐 -¥220；前 5 大是……
```

---

### User Story 3 - 两条总结路径同口径：主路径与兜底路径都不许心算 (Priority: P2)

合计只有一个来源（SQL 聚合）。无论 agent 正常（LLM 自行总结）还是 agent 失败走兜底路由（`graph.py` 固定分类 → `llm.summarize_query_result`），报出的合计都必须一致且正确；LLM 总结不可用时的降级文案同样如此。

**Why this priority**: 兜底路径是故障时用户唯一可用的通道；若只改主路径，故障场景反而继续报错账。降级文案是 SC-010（记账人昵称）的既有承诺，不能被顺手改掉。

**Independent Test**: 强制 agent 失败（或直接调 `graph.py` 兜底函数）→ 查账回复合计与主路径一致；强制总结失败 → 降级文案的支出/收入分开且逐条带昵称。

**Acceptance Scenarios**:

1. **Given** agent 正常，**When** 查账，**Then** 合计来自 `totals`，LLM **MUST NOT** 根据 `records` 自行求和
2. **Given** agent 失败走兜底路由，**When** 查账，**Then** 兜底路径同样先取聚合、再把 `totals` 交给总结——合计与主路径一致
3. **Given** LLM 总结不可用（降级文案），**When** 查账，**Then** 文案展示分开的支出/收入合计，且逐条明细仍带记账人昵称
4. **Given** 已删除账本（只读历史），**When** 查账，**Then** 返回**同一信封结构**（附加 `ledger_deleted`/`notice`），totals 照算

**对话样例**（示意，非规定文案）：

```text
（LLM 总结服务不可用，降级路径）
bot：查到 26 条记录（AI 总结暂时不可用）。
     支出 ¥1,250.00（25 笔）、收入 ¥5,000.00（1 笔）
     · 9-01 居住 -¥800.00（老板）
     · 9-15 餐饮 -¥220.00（小王）
     …

（agent 失败走兜底）
用户：这个月花了多少
bot：本月支出 ¥1,250.00，共 25 笔。
```

---

### Edge Cases

- **少于默认条数**（3 笔 < 5）→ 全列，`total_count` 正确，不补零不截断。
- **limit 越界**（0 / 负数 / 999）→ 钳制到 [1, 50]，不报错。
- **已删除账本** → 与正常查询**同一信封**（`records`/`totals`/`total_count`/`order_by`）+ `ledger_deleted`/`ledger_name`/`notice`；合计照算（历史只读可查）。
- **分类过滤与收支分列组合**（问"餐饮花了多少"，该分类只有支出）→ 收入侧为 0 或缺省，不编造。
- **旧调用方**（e2e/测试直接调 `db.query_by_ledger`）不传 `order_by` → 默认 `recent`，行为与现状一致（不回归）。
- **明细与合计对不上**（只列大头）→ 属设计内，文案须明确"这是金额最大的几笔"，避免误会。

## Requirements *(mandatory)*

### Functional Requirements

**汇总（合计与明细解耦）**

- **FR-001**: 数据层 MUST 提供按账本+日期+过滤条件聚合的合计能力（`db.sum_by_ledger`：`COUNT(*)`/`SUM(amount)`、`GROUP BY type`、**无 LIMIT**），使合计与明细条数彻底解耦。
- **FR-002**: 聚合与明细 MUST 共用同一套日期窗口（`date_from` 归零 + `date_to` 次日，半开区间）与过滤口径（账本/分类/类型）；两者 MUST 抽为同一 helper，禁止各写一份（防止口径漂移）。
- **FR-003**: 合计 MUST 按类型分开（支出/收入各自的 count 与 total），MUST NOT 合并为单一数字。
- **FR-004**: 空账本时聚合 MUST 返回 0（count/total），MUST NOT 返回 NULL 或缺键。

**明细**

- **FR-005**: `db.query_by_ledger` MUST 支持 `order_by` 参数：`recent`（时间倒序，**默认**，保持旧语义）与 `top_amount`（金额倒序）。
- **FR-006**: 查账工具的明细默认 MUST 为 `order_by="top_amount"` + `limit=5`；`limit` MUST 钳制到 `[1, 50]`。
- **FR-007**: 明细类问题（"最近买了啥"）MUST 能取时间序明细——由 LLM 显式传 `order_by="recent"`，工具 docstring MUST 教会这个用法。

**工具返回结构**

- **FR-008**: 查账工具 MUST 返回统一信封 `{records, totals, total_count, order_by}`；**已删除账本分支 MUST 使用同一信封**（追加 `ledger_deleted`/`ledger_name`/`notice`），两种情形键结构一致。
- **FR-009**: 工具 docstring MUST 写明：`totals` 是**完整**合计、不受 limit 影响；回答金额问题**必须**用 `totals`、**禁止**根据 `records` 自行求和；`records` 是金额最大的 ≤limit 笔，与合计对不上属正常。

**总结（两条路径同口径）**

- **FR-010**: `llm.summarize_query_result` MUST 基于 `totals` 产出合计（删除 `sum()` 心算），`totals` 为**必填**参数（防止漏传退回心算）。
- **FR-011**: 主路径（agent 系统提示词查账条目）MUST 同步："金额类问题用 `totals`，不得自行求和"。
- **FR-012**: 兜底路径（`graph.py` 在 agent 失败时的固定路由）MUST 同样取聚合并传入 `totals`——与主路径同口径，MUST NOT 保留"取 20 条再心算"。
- **FR-013**: 降级文案（LLM 总结不可用）MUST 用 `totals` 分开表述支出/收入，且逐条明细 MUST 仍带记账人昵称（SC-010 不回归）。

**不回归**

- **FR-014**: 记账人昵称（正常/降级两条路径）、账本隔离（`ledger_id`）、已删账本只读与提示、记账写入路径 MUST NOT 回归。

### Key Entities

- 无新增实体。新增两类结构：`sum_by_ledger` 的聚合结果 `{type: {count, total}}`；工具返回信封 `{records, totals, total_count, order_by}`（已删账本时附加只读标记字段）。

## Success Criteria *(mandatory)*

- **SC-001**: "花了多少钱"类问题的合计与全量 SQL 求和的偏差 = **0**（含条数 > limit 的场景）。
- **SC-002**: 收入计入支出合计的案例 = **0**；混加的"总金额"数字 = **0 例**。
- **SC-003**: 复现场景归零：25 笔 / ¥1250（大额在月初）→ 报 **¥1250.00**（修复前为 ¥800.00）。
- **SC-004**: 明细条数 ≤ limit 且排序符合 `order_by`；`limit` 越界被钳制（无报错、无穿透）。
- **SC-005**: 已删账本查询与正常查询的**键集合一致**（同一信封）。
- **SC-006**: 记账人昵称保留率 = **100%**（正常与降级路径）。
- **SC-007**: `pytest tests/ -q` 全绿（新增 ≥4 条：聚合正确性 / top_amount 排序 / 收入不计入支出 / 不截断场景）；e2e 保持 16/16；evals 查账用例（"本月支出合计约 80"）在 totals 下**稳定**通过。

## Assumptions

- **默认 limit=5 的触发机制**：LLM 九成时候不传 `limit`，改默认值即改变绝大多数查询的实际行为；需要更多明细的场景由 LLM 显式传大 `limit`（上限 50 兜底，防撑爆上下文/微信消息长度——保险丝语义保留）。
- **明细按金额而非时间排序**：明细的职责是让用户核对合计，大头对得上合计才有说服力；"最近买了啥"由 `order_by="recent"` 保留。
- **工具签名不拆成两个**：一个工具带 `order_by` 参数，好过两个工具让 LLM 学"该调哪个"。
- **收支分开是纠正而非新口径**：原先 `sum()` 把收入支出加在一起（¥10820 这类数字）本身是缺陷。
- **`totals` 必填是防呆**：可选参数会让调用方漏传而悄悄退回心算——必填让编译器/测试替我们盯着。
- **不做**：分页、导出、按成员聚合、趋势图；本期只保证"合计准、明细可核对"。
