# Loop Agent 改造方案：从「固定路由」到「循环决策」

> 目标：把 `graph.py` 从 **一次性意图分类 → 固定三分支** 的管道结构，
> 升级为 **会循环思考、调用工具、观察结果、自主决定下一步** 的 Agent。
> 这是本项目从「一个调用 LLM 的记账工具」升级为「一个 Agent 开源项目」的**核心转型**。

---

## 一、现状：固定路由（改造前）

### 当前流程

```
用户消息
   ↓
classify_node   (1 次 LLM 调用，判断意图：record / query / chat)
   ↓
┌──┬──┬──┐
│记│查│聊│   ← 三选一，固定走一个分支，到 END 就停
└──┴──┴──┘
   ↓
END  (LLM 只参与 1-2 次，做完判断就分道扬镳，没有「观察结果再决策」)
```

### 核心问题

1. **固定路由、无循环**：LLM 只被调用 1-2 次，走完一个分支就结束，无法根据中间结果调整下一步。
2. **查账缺少多步推理**：`query_node` 里，LLM 生成参数 → 查库 → 直接用代码糊成一句话，**LLM 不知道查到了什么，也没机会根据结果细分**。
3. **记账缺少确认闭环**：缺金额时只反问一次，无法做「先确认、再落库」的多步流程。
4. **Agent 属性弱**：这本质是「一次工具调用」，不是「自主决策的 agent」——简历上无法体现 agentic 工程能力。

---

## 二、改造后：Loop Agent（循环决策）

### 核心变化

```
用户消息
   ↓
┌─────────────────────────────────────────────────────────┐
│  AGENT LOOP（循环）                                      │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐          │
│  │  思考      │ →  │  行动      │ →  │  观察      │        │
│  │ LLM决定   │    │ 调用工具   │    │ 看结果     │        │
│  │ 下一步     │    │ 记账/查账  │    │ 再决定     │         │
│  └──────────┘    └──────────┘    └──────────┘          │
│        ↑____________︱______________↑                    │
│                 （直到 agent 判断「任务完成」才停下）        │
└─────────────────────────────────────────────────────────┘
   ↓
END  (agent 自主决定可以收尾了)
```

### 每一圈的三个动作

| 动作 | 做什么 | 例 |
|---|---|---|
| **思考 (Think)** | LLM 看当前状态，决定下一步 | "用户问本月花了多少，我需要查数据" |
| **行动 (Act)** | 调用一个工具 | `query_transactions(date_from, date_to)` |
| **观察 (Observe)** | 看工具返回，判断是否足够 | "拿到 12 笔 ¥820，够回答了，收尾" |

### 关键区别对照表

| | 现在的固定路由 | Loop Agent |
|---|---|---|
| LLM 参与次数 | 1-2 次 | **3-5 次甚至更多** |
| 决策方式 | 一次分类，三选一 | **每轮都重新决策** |
| 对工具结果的反应 | 无（查完就不管） | **每轮都观察结果再决定** |
| 能否分步干活 | 不能 | **能（多步、按需扩展）** |
| 是否自己知道"做完了" | 不知道 | **知道（判断任务完成）** |
| 简历价值 | 一个 LLM 应用 | **一个会自主决策的 Agent** |

## 三、改造要点（怎么从现状做成 loop）

### 1. 图结构：从「三分支直通」改成「循环节点」

现在：
```
START → classify → [record|query|chat] → END
```

改成：
```
START → agent_loop（LLM 反复决策）→ END
```

用 LangGraph 实现，核心是一个**带条件边、能回环**的图：
- `agent` 节点：LLM 思考，返回「下一步动作」
- `tools` 节点：执行 agent 选定的工具，把结果回填
- 条件边判断：**继续循环**（还要调工具）还是 **结束**（任务完成）

### 2. 工具集：从「1 个只读工具」扩展

现在只有 `query_transactions`（只读查询）。要变成 agent 能自主选择，需要加：

| 工具 | 作用 | 现有/新增 |
|---|---|---|
| `query_transactions` | 查账（只读，参数化防注入） | ✅ 已有 |
| `record_transactions` | 记账（多笔入库，事务） | 🆕 新增 |
| `ask_for_amount` | 金额缺失时反问 | 🆕 新增（替代 pending 状态） |
| `summarize` | 总结 / 计算汇总 | 🆕 或由 agent 直接生成回答 |

### 3. 状态：让 agent「每轮都能看到全局」

LangGraph 的 `GraphState` 要承载「对话历史 + 工具结果」，让 agent 每轮思考时能看到：
- 用户原始消息
- 之前调过哪些工具、返回了什么
- 当前进行到哪一步（是否还缺金额、是否查完数据）

这样它才能**基于上一步的结果做下一步决策**。

### 4. 终止条件：agent 怎么知道「完成了」

- **自然结束**：agent 输出「最终回答」，不再调用工具 → 结束
- **兜底设限**：设定最大循环次数（如 6 圈），防止死循环/无限烧钱
- **异常回退**：LLM 失败时回退到当前的最优已有回答

### 5. 与现有接口的衔接

好消息：`main.py` 的入口 `graph.process_message(openid, content)` **不用改**，`openid` 已经一路传下来。改造只发生在 `graph.py` 内部 + `llm.py` 增加 loop 相关的调用。上层微信协议层（wechat.py）、数据库层（db.py）可以保持不动。

## 四、落地步骤（分阶段，每个阶段可独立验证）

### 阶段 A：最小的 loop demo（先跑通，后看懂）⭐ 最先做
- 手写一个**不依赖 LangGraph 的简单循环**，让 LLM 在 3-4 圈里「思考→调工具→观察→再决定」
- 用「这个月花了多少」这个场景验证：agent 会自动查数据 → 看结果 → 决定是否细分 → 输出
- **验证**：能跑通一次真实的多步决策，亲眼看到 agent 会变

### 阶段 B：接入 LangGraph 图
- 把阶段 A 的手写循环改造成 LangGraph 的状态图
- `agent` 节点 + `tools` 节点 + 条件边（循环/结束）
- **验证**：LangGraph 版跑通，图结构在日志里能看到循环轨迹

### 阶段 C：扩展工具集 + 记账闭环
- 加 `record_transactions`、`ask_for_amount` 工具
- 把「缺金额反问」从 pending 状态改成 agent 的自主行动
- **验证**：记账、多笔、金额反问都能走 agent 循环

### 阶段 D：稳定性 + 成本控制
- 最大循环次数设限（熔断）
- 工具结果剪枝（只保留关键字段，控制 token）
- **验证**：复杂对话不会死循环，token 消耗可控

### 阶段 E：开源整理
- README 突出「微信原生 + Agent 自然语言记账」差异化卖点
- 架构图、演示动图
- **验证**：GitHub 上可展示、可跑

## 五、面试/简历讲稿（核心卖点）

> 我把项目从「调 LLM 生成的记账工具」重构成「一个**会自主决策的 Agent**」：
> 用 LangGraph 把固定路由改成**循环思考-调用工具-观察结果的 Agent loop**，
> 让系统能根据工具返回自主决定下一步（查账可细分、记账可确认、金额缺失可反问），
> 并做了**最大循环限流**和**工具结果剪枝**来控制成本。
>
> 技术栈：LangGraph 状态机 + tool calling + 参数化 NL2SQL，解决微信 5 秒回调超时等工程问题。
