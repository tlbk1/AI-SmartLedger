## 1. 背景与目标
### 1.1 产品形态
一个挂在**微信公众号**上的记账机器人。用户在微信里发消息，后端用 LLM 解析成账单并入库；也能用自然语言查询账单统计。
**没有独立 App，前端就是微信。**
### 1.2 为什么做这个
- 砍掉前端 UI 开发，把精力集中在 AI 与业务逻辑（团队强项：Python + LangChain/LangGraph）
- 微信零门槛使用，无需下载安装
- 账单天然适合自然语言交互（"午饭35"比填表快）
### 1.3 MVP 目标
验证核心闭环：**用户发消息 → AI 记账/查账 → 微信回复**。
不包含：会员体系、支付、报表导出、多币种、预算、云同步等。
---
## 2. 目标用户与场景
### 2.1 目标用户
**多人共账场景**：情侣 / 家庭 / 合租室友 共用一个账本，需要区分"谁记的这笔账"。
> 设计前提：数据模型从一开始就支持「账本—用户」多对多关系，即便 MVP 只有一个用户也能平滑扩展。
### 2.2 核心场景（MVP 只做前两个）
| # | 场景 | 示例对话 | 是否 MVP |
|---|---|---|---|
| 1 | 记一笔 | "午饭35" → "✅ 已记：餐饮 支出 ¥35" | ✅ |
| 2 | 查账 | "这个月餐饮花了多少" → "本月餐饮支出 ¥820，共 12 笔" | ✅ |
| 3 | 记多笔 | "午饭35，打车12" → 一次解析两笔 | ✅ |
| 4 | 改/删账 | "删掉刚才那笔" | ❌ 阶段2 |
| 5 | 闲聊 | "你好" → 友好回复 | ✅ 兜底 |

## 3. 功能需求
### 3.1 微信接入
- **F1.1** 接入微信公众号（订阅号起步，后续升级服务号）
- **F1.2** 接收用户消息，完成微信签名校验与 XML 解析
- **F1.2a** **MsgType 闸门**：只处理 text 类型消息；event（subscribe）回欢迎语，image/voice/location 等回空串，不进入主流程（事件消息无 MsgId/Content，按文本处理会 KeyError）
  > 评审修正：遗漏1 — 用户关注/扫码时微信会 POST event 消息，与 text 结构不同，必须分流
- **F1.3** 处理 5 秒超时约束：优先 5 秒内被动回复；超时则用**客服消息接口**主动推送
  > 重试机制澄清：空串只要 5 秒内到达即视为成功应答，微信不会重试。重试只发生在"5 秒内微信什么都没收到"时（网络慢、进程卡死）。因此幂等去重（14.1）防的是网络抖动导致重试的情况。
  > 超时处理实现：不能用 `asyncio.wait_for`（它会 cancel 任务，后台结果被丢弃）。正确做法：`create_task` + `shield` + `done_callback`——超时返回空串，但 shield 保护的任务继续跑，跑完由 callback 推客服消息
- **F1.4** 识别用户身份：通过微信 openid 区分不同用户
### 3.2 AI 记账（核心）
- **F2.1** 解析自然语言为结构化账单，字段：
	- 类型（支出/收入/转账，MVP 只做支出+收入）
	- 金额（必填，缺失则追问）
	- 分类（支出：餐饮/交通/购物…；收入：工资/兼职…）——由 LLM 推断
	- 备注（可选，原文片段）
	- 时间（默认当前时间，支持"昨天""上周五"等）
	- 记账人（当前 openid 对应的用户）
- **F2.2** 支持一次解析多笔（"午饭35，打车12"）
- **F2.3** 金额缺失/歧义时，反问用户而不是瞎记
- **F2.4** 返回格式化确认消息
### 3.3 AI 查账
- **F3.1** 支持自然语言查询，维度：时间范围、分类、记账人
- **F3.2** 示例："本周花了多少""老婆这个月餐饮多少""最近5笔"
- **F3.3** LLM 通过**工具调用(tool calling)** 执行 SQL 查询，再总结成自然语言回复
- **F3.4** 只读，不修改数据
### 3.4 账本与成员（为共账预留）
- **F4.1** 一个账本（ledger）可包含多个成员
- **F4.2** 用户首次发消息自动创建「默认账本」，自己作为唯一成员
- **F4.3** MVP 暂不做"邀请加入账本"功能，但表结构预留

## 5. AI 流程设计（LangGraph）
```javascript
用户消息
   │
   ▼
[意图识别节点] ──┬─→ 记账意图 ──→ [记账节点] ──→ 入库 ──→ 回复确认
                ├─→ 查询意图 ──→ [查询节点(工具调用)] ──→ 查DB ──→ 回复统计
                └─→ 其他 ─────→ [闲聊节点] ──→ 友好回复
```
- **状态(State)**：跨节点传递对话上下文、当前用户、账本
- **记账节点**：LLM 结构化抽取 → 校验金额/分类 → 写入 transactions
- **查询节点**：LLM 生成查询参数 → 调用 `query_transactions` 工具(SQL) → LLM 总结结果
- **异常处理**：LLM 失败/超时 → 回"稍后再试"，不丢消息

当前：**个人，无营业执照**。带来的限制：
| 能力 | 个人订阅号 | 认证服务号（需企业） | 微信测试号 |

| 注册 | ✅ | ❌ 需营业执照 | ✅ |

| 微信支付 | ❌ | ✅ | ❌ |
| 域名备案要求 | 需备案 | 需备案 | 不需要 |
| 用户量上限 | 有 | 无 | 仅测试号自己+少量体验者 |
**结论与推进路径**：
1. **开发阶段**：用**微信测试号**跑通「消息→LLM→记账→回复」闭环，无需任何资质、无需备案、本地 HTTP 即可。
2. **小范围试用**：测试号可加少量体验者（100 人内），够情侣/家庭/室友自用。
3. **正式上线**：若要面向公众，二选一——
	- 路线 A：注册**个体工商户**（个人可办，成本最低的企业形态），认证服务号，解锁客服消息+支付。
	- 路线 B：保持个人订阅号，接受「5秒内被动回复」限制，用轻量 LLM / 提前确认等手段压住延迟。
> 注：个体工商户营业执照个人即可办理，线上「政务服务网」或线下市场监管局，通常免费，1-3 个工作日。是「无企业」状态升级到认证服务号的最便宜路径。

## 11. 技术细节（2026-08-14 敲定）
### 11.1 开发环境（家用电脑）
- 开发期**不需要公网服务器**，本地跑 FastAPI + 内网穿透暴露给微信测试号回调
- **内网穿透**：cpolar / natapp（国内，稳定，微信回调友好）
- 数据库：SQLite（开发起步，单文件零配置）
- 部署上线时再考虑云服务器 + 备案域名（见 Q3）
### 11.2 LLM 接入
- **改用公司中转站**（不再直调 DeepSeek 官方）
- **Base URL**：`https://ccc.szprize.cn/v1`（OpenAI 兼容格式，`/chat/completions`）
- **模型**：`claude-haiku-4-5-20251001`
- **调用方式**：用官方 `openai` Python SDK，只需把 `base_url` 指向中转站、`api_key` 填中转站 key，其余和调 OpenAI 一样
- **认证**：`Authorization: Bearer sk-**`（中转站 key，存本地 `.env`，变量名 `LLM_API_KEY`）
- 用途：① 结构化抽取（消息→账单字段）② 工具调用（查账）
- 调用示例：
```python
from openai import OpenAI
client = OpenAI(
    base_url="https://ccc.szprize.cn/v1",
    api_key=os.environ["LLM_API_KEY"],
)
resp = client.chat.completions.create(
    model="claude-haiku-4-5-20251001",
    messages=[{"role": "user", "content": "..."}],
)
```
> 注：原计划用 DeepSeek，现改为公司中转站 + Claude Haiku 4.5。DeepSeek key 作为备用保留。
### 11.3 数据库（极致简化·单表）
> MVP 单用户自用，只建 `transactions` 一张表。共账相关的 users/ledgers/ledger_members/categories 等表暂不建，以后要共账时再加，迁移成本低。
**`transactions`**** 账单表**

> 注：单用户省掉了 user_id、ledger_id、category_id 外键；分类直接存中文字符串而非外键，简化 AI 写入。

## 14. 技术决策与工程补充（2026-08-14 评审后敲定）
### 14.1 微信消息幂等（防重复记账）
- 微信 5 秒无响应会**重试同一消息**（最多 3 次），不去重会重复记账
- **决策**：收到消息先查 msgid 去重缓存（内存 dict，key=msgid，TTL 10 分钟）；命中则直接回 ACK 不再处理
- 重启丢失缓存可接受：重试窗口（秒级）远小于重启频率
### 14.2 回复策略与客服消息限制
- 客服消息只能发给 **48 小时内互动过的用户**（自用场景几乎总是满足）
- **决策**：优先在 5 秒内被动回复（Haiku 快，多数 \<3s）；超时才走客服消息推送
- 推送失败（超 48h）：记日志，用户下次发消息时附上未送达结果
### 14.3 对话状态（反问机制）
- 问题：用户回「35」时，怎么知道是上一笔的补充而不是新的一笔？
- **决策**：内存 dict `pending[openid] = {question, draft, ts}`，TTL 10 分钟
	- 用户回复先查 pending：有 → 当作对反问的回答，合并 draft 再走记账；无 → 正常意图识别
	- 单用户内存态足够；重启丢 pending 只会让用户重发一次，可接受
	- 升级路径：阶段 2 多用户时换 SQLite 表存
### 14.4 NL2SQL 安全（重要）
- **不让 LLM 写 SQL 字符串**。工具 schema 只收结构化参数：`{date_from, date_to, category?, type?, limit}`
- 代码内用参数化查询拼 SQL，天然免疫注入
- **日期边界陷阱**：LLM 产出日期级参数（`2026-08-31`），库里存完整时间戳（`2026-08-31T08:00:00`）。若用 `BETWEEN '2026-08-01' AND '2026-08-31'`，字符串比较时 `2026-08-31T08:00 > 2026-08-31`，最后一天当天所有账目被排除
  > 评审修正：错误2 — 改用半开区间 `happened_at >= date_from + T00:00:00 AND happened_at < date_to次日 + T00:00:00`
- 工具只读：仅 SELECT，代码里不存在 DELETE/UPDATE 路径
### 14.5 签名校验与消息格式
- 校验算法：`SHA1(sort(token, timestamp, nonce))` 与 query 里的 signature 比对；GET 验证原样返回 echostr
- 消息模式：**明文模式**（测试号 + MVP 不用加解密，最简）
- XML 取用字段：ToUserName / FromUserName / MsgType=text / Content / MsgId / CreateTime
### 14.6 边界场景决策
| 场景 | 决策 |
|---|---|
| 多笔部分失败 | 整批一个 SQLite 事务，全成或全不记；失败回「没记上，请重发」 |
| 金额单位 | 默认元；用户显式说「分」才按分；不做自动猜测 |
| 时区 | 统一 Asia/Shanghai；SQLite 存 ISO 本地时间字符串；prompt 里注入当前时间 |
| 闲聊 vs 记账灰区 | 无金额且无查询意图 → 闲聊；「今天花了好多」无具体金额 → 反问要金额 |
| LLM 格式错误 | JSON schema 约束输出；解析失败重试 1 次，再失败回「稍后再试」 |
| 分类不确定 | 不追问（太啰嗦），LLM 直接给最佳猜测，拿不准归「其他」 |

### 14.8 微信 access_token 管理（客服消息前置）
- 客服消息等主动接口需要 access_token，有效期 7200 秒；每日获取有调用上限（约 2000 次/天），**不能每次请求都去取**
- **决策**：内存缓存 token，过期前 5 分钟懒刷新（用时检查，快过期才重新获取）；单进程内存即可，MVP 无需集中式缓存
- 获取：`GET https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=...&secret=...`
- **失效兑底**：调客服消息返回 40001/42001（token 失效）→ 强制刷新一次并重试原请求
- 注：测试号与正式号该机制一致，代码不用改
