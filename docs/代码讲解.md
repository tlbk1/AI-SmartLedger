## 0. 先看全景：一条消息的完整旅程

用户在微信里发「午饭35」，系统里发生了什么：

```
 用户微信                微信服务器            你的电脑（cpolar 隧道 → 本地 8000 端口）
   │                       │                        │
   │──"午饭35"────────────▶│                        │
   │                       │──POST XML───────────▶ │ main.py  /wechat 路由
   │                       │  (带签名)              │   │
   │                       │                        │   ├─① wechat.py  验签名
   │                       │                        │   ├─② wechat.py  解析 XML
   │                       │                        │   ├─③ db.py      去重（msgid 查小本本）
   │                       │                        │   ├─④ graph.py   进 LangGraph 流程
   │                       │                        │   │    ├─ 分类：record（要记账）
   │                       │                        │   │    ├─ llm.py 抽取 → {餐饮, 35元}
   │                       │                        │   │    └─ db.py  写入 SQLite
   │                       │                        │   └─⑤ wechat.py 组装回复 XML
   │                       │◀──回复 XML ───────────│
   │◀──"✅ 已记：餐饮 ¥35"──│                        │
   │                       │                        │
   │  （如果 5 秒没回，微信会重发 → 被③去重挡掉）      │
```

## 1. 文件地图：谁负责什么

```
AI-SmartLedger/
├── main.py        ← 门卫+调度中心：接 HTTP 请求，决定走哪条路
├── wechat.py      ← 微信语翻译官：签名/XML/token，全是微信特有的东西
├── graph.py       ← 大脑：意图路由（记账？查账？闲聊？）+ 对话状态
├── llm.py         ← AI 嘴巴：所有跟大模型对话的代码
├── tools.py       ← 安全查询接口：LLM 只能通过它查数据库，摸不到 SQL
├── db.py          ← 记忆：SQLite 存账单 + 两个内存小本本（去重/反问状态）
├── .env           ← 密钥配置（不进 git）
└── tests/         ← 18 个测试，不联网不花钱就能验证核心逻辑
```

**依赖方向**（谁 import 谁）：

```
main.py ──▶ wechat.py
    │
    └────▶ graph.py ──▶ llm.py ──▶ tools.py
              │            │          │
              └────────────┴────▶ db.py
```

main 是入口，db 是地基，中间三层各管一段。**没有循环依赖**——像洋葱一样一层包一层，内层不知道外层的存在。

## 2. main.py — 门卫与调度（约 180 行）

### 2.1 两个路由

**GET /wechat**（只发生一次：你在微信后台填 URL 点提交时）

```python
@app.get("/wechat")
async def wechat_verify(request: Request):
    # 微信发来 4 个参数：signature / timestamp / nonce / echostr
    if wechat.verify_signature(signature, timestamp, nonce):
        return PlainTextResponse(echostr)      # 暗号对上 → 原样回 echostr
    return PlainTextResponse("Forbidden", status_code=403)  # 对不上 → 拒绝
```

这就是之前讲过的"对暗号"：微信拿你填的 Token 算了个哈希发过来，你拿自己的 Token 也算一遍，对得上就证明这个 URL 真的是你的服务器。

**POST /wechat**（用户每发一条消息触发一次）——核心流水线：

```
[A] 验签名 ──失败──▶ 403
     │通过
[B] 解析 XML ──失败──▶ 回空串
     │成功
[B'] 消息类型闸门：不是 text？
     │              ├─ subscribe 事件 ──▶ 回欢迎语
     │              └─ 其他 ──────────▶ 回空串（不处理）
     │是 text
[C] 去重：msgid 在小本本里吗？
     │              └─ 在 ──▶ 回空串（丢弃重试）
     │不在
[E] 扔进线程池跑 LLM 流程，同时开始计时 ⏱️ 4.5 秒
     ├─ 4.5s 内完成 ──▶ 快路径：结果塞回 HTTP 响应（用户秒收）
     └─ 超时 ────────▶ 慢路径：先回空串占位，
                        后台跑完后再用"客服消息"主动推给用户
```

### 2.2 全项目最 tricky 的 10 行：超时降级

微信规定：**5 秒内必须响应，否则它重发消息**。而 LLM 可能要跑 3~8 秒，怎么办？

```python
task = asyncio.create_task(
    asyncio.to_thread(graph.process_message, openid, content)  # 扔线程池
)
try:
    # shield 是关键：超时后 wait_for 只取消"等待"，不取消任务本身
    reply = await asyncio.wait_for(asyncio.shield(task), timeout=4.5)
    return 快路径回复
except TimeoutError:
    # 任务还活着！注册一个"跑完时叫我"的回调
    task.add_done_callback(推客服消息)
    return ""   # 先给微信一个空串占位
```

**为什么这么绕？** 因为 `wait_for` 的默认行为是"超时 = 杀掉任务"。直接用的话，超时后 LLM 结果就算出来了也被扔掉，用户永远收不到回复。

三层保护各司其职：
- `create_task`：让任务独立于本次 HTTP 请求存活
- `shield`：超时只是"我不等了"，任务继续跑
- `done_callback`：任务完成的那一刻，自动把结果推向客服消息接口

> 🕳️ 踩坑记录：我第一版写成 `create_task(asyncio.shield(...))`，直接 TypeError 崩溃——因为 shield 返回的是 Future 不是协程，create_task 不收。正确顺序是 **先 create_task，等待时再套 shield**。

### 2.3 同步还是异步？

一个容易困惑的点：路由函数是 `async def`，但里面的处理逻辑全是**同步**的（sqlite3 是同步库，OpenAI SDK 我们也用同步调用）。

答案是 `asyncio.to_thread` ——它把同步函数扔进线程池，事件循环继续接别的请求，不被 LLM 的 3 秒等待卡死。单用户量级下这是最省事的方案（需求文档 14.7 的决策）。

## 3. wechat.py — 微信语翻译官（约 200 行）

**设计原则：所有微信特有的脏活（签名、XML、token）关在这一个文件里，其他模块完全不知道微信协议的存在。** 哪天要换成钉钉机器人，只需要重写这个文件。

### 3.1 签名校验（5 行核心）

```python
def verify_signature(signature, timestamp, nonce):
    parts = sorted([WECHAT_TOKEN, timestamp, nonce])   # 三个值字典序排序
    raw = "".join(parts)                               # 拼成一个字符串
    our_hash = hashlib.sha1(raw.encode()).hexdigest()  # 算哈希
    return our_hash == signature                       # 跟微信发来的比
```

Token 从不走在网络上，双方各自用它算哈希来对暗号。

### 3.2 XML 解析

微信发的是 XML 不是 JSON：

```xml
<xml>
  <FromUserName><![CDATA[用户openid]]></FromUserName>
  <MsgType><![CDATA[text]]></MsgType>
  <Content><![CDATA[午饭35]]></Content>
  <MsgId>1234567890123456</MsgId>
</xml>
```

两个注意点：
- 用 `defusedxml` 而不是标准库 `xml.etree` ——防"XML 炸弹"（恶意构造的 XML 能耗尽内存）。虽然签名挡住了绝大多数坏人，多一层保险不要钱
- **事件消息没有 MsgId 和 Content**！用户扫码关注时发的是 `<Event>subscribe</Event>`，如果代码无脑取 `MsgId` 会直接 KeyError。所以解析函数对缺失字段都返回空串兜底

### 3.3 被动回复：方向是反的！

收到消息时：`To=公众号`，`From=用户`
回复消息时：**`To=用户`，`From=公众号`** ——像回信一样，收发人对调。

```
<xml>
  <ToUserName><![CDATA[用户openid]]></ToUserName>      ← 收件人=用户
  <FromUserName><![CDATA[gh_xxx]]></FromUserName>      ← 发件人=公众号
  <Content><![CDATA[✅ 已记：餐饮 ¥35]]></Content>
</xml>
```

这是新手最常翻车的点（写反了用户收不到回复），tests 里专门有个测试守着这个方向。

### 3.4 access_token：微信世界的临时通行证

客服消息等"主动接口"不能白调，要先出示 access_token（有效期 2 小时，每天最多取 2000 次）。

```
                    ┌─────────────────────────────┐
   要发客服消息 ───▶ │ token 缓存还有效（>5分钟）？   │
                    └───────┬─────────────┬───────┘
                       是   │             │  否（快过期/没有）
                            ▼             ▼
                      直接用缓存      向微信申请新 token，存起来
```

**懒刷新**：不是定时器定时刷新，而是"每次要用时检查一下，快过期才去换"。单用户场景一天可能就刷几次，远低于限额。

**兜底**：如果缓存的信息过期了微信返回 40001/42001，就强制刷新一次再重试。缓存再聪明也有失手的时候，失败重试是最后的安全网。

## 4. db.py — 记忆（约 190 行）

三层结构，从上往下：

### 4.1 两个内存小本本（_TTLCache）

| 小本本 | key | 存什么 | 解决什么问题 |
|--------|-----|--------|-------------|
| `seen` | msgid | "这条消息见过了" | 微信 5 秒超时重发 → 不重复记账 |
| `pending` | openid | 半成品账单 + 反问的问题 | 反问"金额多少？"后用户回"35" → 知道这是补金额 |

`_TTLCache` 是个 30 行的轮子（没用第三方库）：字典 + 每个条目带过期时间戳 + 线程锁。10 分钟自动过期——反问完两小时后才回消息，就不该再当补金额处理了。

### 4.2 SQLite 单表

```sql
CREATE TABLE transactions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    type        TEXT NOT NULL,     -- expense / income
    amount      REAL NOT NULL,     -- 金额（元）
    category    TEXT NOT NULL,     -- "餐饮"（直接存中文，不建分类表）
    note        TEXT,
    happened_at TEXT NOT NULL,     -- ISO 时间字符串
    created_at  TEXT NOT NULL
)
```

单用户 MVP 极致简化：没有 user 表、没有外键、分类就是字符串（需求文档 11.3）。

**多笔事务**（"午饭35，打车12" 一次记两笔）：

```python
with conn:                      # 上下文管理器 = 自动事务
    for t in txns:
        conn.execute("INSERT ...", t.to_row())
# 全部成功 → commit；任何一笔失败 → 全部回滚
```

要么两笔都记上，要么一笔都不记，绝不出现"记了一半"。

### 4.3 查询的日期边界陷阱

**坑**：LLM 给的是日期 `"2026-08-31"`，库里存的是完整时间 `"2026-08-31T08:00:00"`。字符串比较时后者更大，如果用：

```sql
WHERE happened_at BETWEEN '2026-08-01' AND '2026-08-31'   -- ❌ 8/31 当天全丢！
```

**解法**：半开区间，把结束日期推到次日零点：

```sql
WHERE happened_at >= '2026-08-01T00:00:00'
  AND happened_at <  '2026-09-01T00:00:00'    -- ✅ 完整覆盖 8 月
```

tests 里有专门的测试：插入一条 8/31 晚上 20:00 的账，查 8 月必须能查到。

## 5. llm.py — AI 嘴巴（约 320 行）

### 5.1 客户端：一行配置接入中转站

```python
client = OpenAI(

```

中转站转发请求到 Claude Haiku，代码侧跟调 OpenAI 一模一样。哪天中转站挂了切 DeepSeek，只改 `.env` 三行，代码不动。

### 5.2 四个函数，各管一件事

```
classify_intent()        "午饭35" → record    "这周花了多少" → query    "你好" → chat
        │
        ▼
extract_transactions()   "午饭35" → {type:expense, amount:35, category:餐饮, ...}
        │                "打车回家" → 需要反问金额！（返回 need_amount=true）
        ▼
extract_query_params()   "这个月餐饮" → {date_from:08-01, date_to:08-31, category:餐饮}
        │
        ▼
summarize_query_result() 数据库的 12 行记录 → "本月餐饮支出 ¥820，共 12 笔"

chat_reply()             兜底闲聊
```

### 5.3 两个防 LLM 抽风的关键手段

**手段一：tool calling 强制结构化输出**

不让 LLM 自由发挥写文本，而是强制它"调用一个工具"，工具的参数 schema 由我们定义：

```python
tool_choice={"type": "function", "function": {"name": "set_intent"}}
# LLM 只能输出：{"intent": "record"} 或 {"intent": "query"} 或 {"intent": "chat"}
# 想输出别的？格式不允许
```

**手段二：失败重试 1 次**

LLM 偶尔会输出坏 JSON。第一次解析失败不要立刻放弃，把请求再发一次（temperature=0 时两次输出通常一致，第二次大概率正常）。两次都失败才降级回"没太明白，能再说一次吗？"

### 5.4 Prompt 里必须塞的两样东西

1. **当前时间**（"昨天""上周五"只有知道今天才能换算成具体日期）
2. **分类清单**（只准用：餐饮/交通/购物/居住/娱乐/医疗/其他 + 工资/外快/其他。不塞清单 LLM 会自创"下午茶"这种分类）

## 6. tools.py — 安全查询接口（约 90 行）

**整个项目安全设计的核心，就一句话：LLM 永远不写 SQL，只填表。**

LLM 看到的只是这个"表格"：

```
┌─ query_transactions 查询单 ──────────────┐
│ 日期从：______-__-__   （必填）            │
│  日期到：______-__-__   （必填）            │
│  分类：☐餐饮 ☐交通 ☐购物 ...（选填）      │
│  类型：☐支出 ☐收入           （选填）      │
│  条数：____                （默认20）      │
└──────────────────────────────────────────┘
```

它填好表交给代码，代码拿参数拼**参数化查询**：

```python
sql = "SELECT * FROM transactions WHERE happened_at >= ? AND happened_at < ?"
if category:
    sql += " AND category = ?"      # ? 是占位符，值单独传
    args.append(category)
conn.execute(sql, args)             # 参数化 = SQL注入免疫
```

就算 LLM 被 prompt injection 唆使输出 `category = "x'; DROP TABLE transactions; --"`，参数化查询也只把它当**一个普通的字符串值**去匹配，不会执行。而且这个文件里根本不存在 DELETE/UPDATE 语句——想删库？无路可走。

## 7. graph.py — 大脑（约 230 行）

### 7.1 状态图

```
              ┌──────────┐
     START ──▶│ classify │  意图识别（先查 pending，见 7.2）
              └────┬─────┘
        ┌──────────┼──────────┐
        ▼          ▼          ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │ record │ │ query  │ │  chat  │
   └───┬────┘ └───┬────┘ └───┬────┘
       ▼          ▼          ▼
      END        END        END
```

LangGraph 的价值：State（一个字典）在节点间流动，每个节点读它、改它。以后加"删账"功能只需新增一个节点，主流程不动。

### 7.2 反问机制 + 护栏

场景：用户说"打车回家"（没金额）→ 机器人反问"金额是多少？" → pending 小本本记下半成品 → 用户回"35"。

**护栏**（不加会误判）：pending 命中后，不能无脑把新消息当金额——万一用户反问窗口里改问"这个月花了多少"呢？

```python
pending = db.get_pending(openid)
if pending is not None:
    if looks_like_amount(content):      # 正则：纯数字/"35元"/"+35" 这类
        合并 draft，直接完成记账        # ✅ "35" → 补金额
    else:
        db.clear_pending(openid)        # ❌ "这个月花了多少" → 当新消息正常处理
```

`looks_like_amount` 就一个正则 `^[+-]?\d+(\.\d{1,2})?(元|块|毛|角|分)?$`，简单但挡住了大部分误判。

### 7.3 容错：没有 LangGraph 也能跑

`build_graph()` 返回 None（比如 langgraph 没装上）时，自动降级为手写的 dispatch（同样的节点函数，手动串起来）。核心逻辑在节点函数里，编排层可替换。

### 7.4 未送达消息补发

客服消息推送失败（比如用户超过 48 小时没互动）→ 文本进 undelivered 队列 → 用户下次发消息时，把积压的回复补发在前头。

## 10. 已知边界（MVP 有意不做的）

- **内存态**：去重缓存、pending、undelivered 都在内存里，重启即失。单用户可接受（需求文档 14.1/14.3 明确决策）
- **单进程**：N2 并发不做，uvicorn 单 worker 跑
- **明文模式**：微信消息不加密（测试号够用，正式号再上安全模式）
- **无用户体系**：所有账单进同一张表，openid 只用来区分对话状态

## 11. 面试/复盘时的讲点（按含金量排序）

1. **5 秒超时竞态**：微信重试机制 → msgid 幂等去重；LLM 慢 → shield + done_callback 双路径回复（快路径塞回 HTTP 响应 / 慢路径客服消息推送）
2. **NL2SQL 安全**：LLM 只填结构化参数，参数化查询 + 只读设计，注入在架构上不可能而不是靠过滤
3. **日期半开区间**：字符串比较的隐秘陷阱，一行 SQL 的边界 bug 用回归测试锁死
4. **对话状态管理**：反问-补答的 pending 机制 + looks_like_amount 护栏防误判
5. **access_token 经济学**：懒刷新 + 失败兜底，在限额内优雅调度
